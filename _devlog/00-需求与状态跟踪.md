## 第三十二批：v3.9.12 修 v3.9.11 引入的回归（09-27 凌晨）

### 用户
> "怎么又产生新的bug了呢。现在这个捉虫一点都点不动了，而且不知道生成的是在右下角，
>   为什么点击一下直接就跑左上角了，现在无论拖动右键都没有任何反应，反而底下的文件夹在动"

**用户说得对，这是我上一次改动引入的回归。**

### 🔴 真根因：`setMouseTakeover(false)` 写在提前 return 之后 → 永远执行不到
```js
function onUp(e) {
  const d = drag.current;
  if (!d || d.id !== e.pointerId) return;  // ← 这里提前返回
  drag.current = null;
  setMouseTakeover(false);                  // ← 永远执行不到！
}
```
一旦 `pointerId` 不匹配或 `drag.current` 已为 null，**永远不会解锁** →
主进程的 `takeoverLocked` 永久为 true → 轮询彻底停摆 → **宠物完全失联**
（点不动、拖不动、点击穿到桌面 = 用户说的"底下的文件夹在动"）。

### 连带修的两个问题
| 问题 | 原因 | 修 |
|---|---|---|
| "点一下直接跑左上角" | 拖动断了之后，遗留的 pointer 状态让宠物瞬移到 (0,0)，并写进了 localStorage 持久化 | 同上的解锁修复；拖动/飞行期间**实时上报位置**，不再用旧 hitbox 判定 |
| 拖动中途会断 | 拖动是直写 DOM（结束时才 setDock），而 hitbox 上报只在 React effect 里做 → 宠物拖出旧区域后主进程判定"不在可交互区"→ 穿透 → pointer capture 失效 → **拖动断掉** | ① 拖动/飞行每帧 `registerHitArea` 实时上报；② 拖动开始 `setMouseTakeover(true)` 钉住，结束解锁 |

### 防御措施（防止再犯）
- **主进程加 20 秒看门狗**：即使页面没发解锁（崩溃/事件丢失），也自动释放，**绝不永久钉死**
- `cancelInteraction`（pointercancel/失焦兜底）同样释放解锁

### 验证（在用户正在运行的程序里，真实鼠标）
| 功能 | 结果 |
|---|---|
| 左键单击 | ✅ 打开聊天 |
| 右键 | ✅ 弹出 7 项菜单 |
| 点「动作与设置」 | ✅ 菜单关 + 设置面板开 |
| 点「玩个动作」 | ✅ 执行 |
| 拖动 | ✅ (180,120) → (390,252) 跟随鼠标 |
| 位置持久化 | ✅ 写入 localStorage |

**测试**：301 条全过；**线上**：`dfcf1c03`；**安装包**：已更新（R2 + 桌面）

### 🔑 教训
**在函数里加"提前 return"时，必须确认后面的清理/解锁代码不会被跳过。**
这类"资源释放写在 early return 之后"的 bug，表现是"功能永久失效"，非常难查。
凡是成对的操作（lock/unlock、open/close、start/stop），释放动作一律放在**最前面**。

→ 用户的 `mouseup` 落到了桌面 → "点击直接跳到页面下面的东西了"。

**修**：新增 **`pet-mouse-held`** 通道 —— 页面监听 window 的 pointerdown/pointerup（捕获阶段），

覆盖 click/contextmenu 等后续事件，保证整个"按下-抬起"都发生在窗口内。

## 第三十八批：v3.9.18 修"记录待办被当成改任务"（09-27）

### 用户（原话）
> "还是ai智障，明天11点需要修改500promax的链接"
> "没找到要改的任务。说具体点？比如「把开会改到明天下午3点」。"
> "记录待办，明天11点需要修改500promax的链接"
> "没找到要改的任务。……"

### 根因（两处）
1. **「修改」两个字被当成"改已有任务"的信号**：
   旧规则 `/(改到|改成|…|修改)/` 只要命中就判定为更新意图 ——
   而用户句子里"修改"是**任务内容的一部分**（要做的事就是"改链接"）。
   连"记录待办，"这么明确的新建前缀都被无视。
2. **标题被剥成残渣**：`stripHelp` 里 `^(?:记录|记事|记)[\s，,：:、]+` 要求"记"后紧跟标点，
   而"记录**待办**，"匹配不上 → 走下面只认"记"的规则 → 剥掉"记"留下"录待办"
   → 标题变成"**录待办， 需要修改500promax的链接**"。
3. 放宽任务标记词：原清单没有"需要/要/修改/链接/核对/确认/更新/联系/跟进"这类
   常见工作动作 → "明天11点需要修改链接"被判成闲聊。

### 修复
| 改动 | 内容 |
|---|---|
| 新增 `UPDATE_INTENT` | 只有出现「改到/改成/改为/推迟到/调整到/修改为」这类**明确变更词**才算改任务；光有「修改」不算 |
| 新增 `CREATE_INTENT` | 句首/动词+名词组合（记录待办、帮我记个待办、添加任务）→ 直接走新建，不进改任务分支 |
| 修 `stripHelp` | "记录/记事/记"连同后面的待办/任务名词一起剥，不再剥一半 |
| 扩充任务标记词 | 加：需要/要X/得X/必须/链接/核对/确认/更新/修改/联系/跟进/提交/上传/邮件/文件… |

### 验证（用户原话那两句 + 反面用例）
| 输入 | 修复前 | 修复后 |
|---|---|---|
| 明天11点需要修改500promax的链接 | ❌ 没找到要改的任务 | ✅ **建任务**（时间 11:00）|
| 记录待办，明天11点需要修改…链接 | ❌ 同上 | ✅ **建任务**（标题干净）|

## 第四十三批：Windows Actions checkout 修复（09-27 下午）

### 用户报的问题

### 排查结论（实测）
1. **本地 git 库是干净的**：HEAD 树里中文名是原始 UTF-8 字节（`od -c` 验证过）；
   默认 `git ls-tree` 显示的 `"_devlog/00-\351..."` 只是 `core.quotepath` 的**显示转义**。
   全库 115 个提交 / 438 棵树 / 6660 条目扫描：**0 个**名字真带 `"` 或 `\`。
2. **坏的是远端**：GitHub 上 `master`（`2ca6ccb`，接口推的）和标签 `v3.9.21`（`1367bf0`）
   的树里，文件名**字面**就是 `_devlog/"00-\351...md"`（真引号 + 真 `\3\5\1` 字符），
   还有 `desktop/"启动桌面版.bat"` —— 共 **10 个**。与用户报的报错逐字节一致。
3. **根因**：`tools/push-via-api.mjs` 里 `git ls-tree <sha>`（**没加 `-z`**）→ git 把中文名
   渲染成带引号转义 → 脚本当字面路径上传 → 远端树存坏。
   （该脚本是网络封锁时写的 API 推送工具，main 是正常 `git push` 推的，所以 main 干净。）
4. **数据安全**：远端两个坏链路的 blob 集合与本地完全一致（逐 blob 比对，0 个独有）→

## 第四十五批：修「说了记下了、待办里却没有」（v3.9.22，2026-09-27）

### 用户报的原话

> 「明天要跟进vivo锁机事项」
> → 轻宜：「好，我帮你记下了：\n「要跟进vivo锁机事项」\n⏰ 2026-09-28」

这是**最伤人的一类**：不是它编了话，是**它真的做了、话是诚实的**，数据却被
另一个窗口悄悄抹掉 —— 用户看到的就是"它在骗我"。

### 查清了什么（都是实跑，不是猜的）

| # | 查什么 | 结果 |
|---|---|---|
| 1 | 复现原话跑对话大脑 | 确实吐 `addTask`，回话与用户截图**一模一样** → **大脑没错** |
| 2 | 读用户机器上真实的 `lighttodo:work:v1` | 41 条任务，**没有这条**；最近一条建于 **9/22** → 确实没存住 |
| 3 | 桌宠窗口写盘了吗 | 静态追 `answer→runAction→onAddTask→addTask`，**每一环都对，确实写了** |
| 4 | 那是谁抹的 | **主窗口**：它每 30 秒 / 每次窗口获得焦点，就把**服务器旧数据整份替换**本地并回写 |

### 根因

桌面版是**两个窗口共用一份 localStorage**：
① 主窗口（完整网页界面）② 桌宠窗口（常驻桌面那只）。

主窗口的任务列表在**内存**里，只在"自己"改动时才更新；
它的防覆盖时间戳也**只有它自己会赋值** —— **看不见桌宠的写入**。

**→ 桌宠记的待办，存活最多 30 秒。**
**→ 更糟的是：用户去主窗口找它，这个"点一下窗口"的动作正好触发拉取 —— 所以永远找不到。**

### 修了什么（`src/lib/syncLock.ts` 新文件）

1. **写盘即登记水位** —— 本窗口写一次就记一个时间戳
2. **水位包含桌宠写的** —— 从**磁盘**读任务/备忘的 `updatedAt` 最大值（磁盘是两窗口共用的）
3. **判据换成"谁更新"** —— 本地比服务端新就拒绝覆盖（原来只认"本窗口有没有编辑过"）
4. **跨窗口互听** —— 主窗口也订阅 `storage` 事件，另一个窗口一改立刻重读
5. **没变就不写** —— 防两个窗口把对方的新数据写回去、无限对写
6. **`normalizeTask` 保留 `updatedAt`** —— 原来会刷成"现在"，等于"读一下就把水位抬高"

### 🔴 修的时候差点弄坏两件事（都已加测试锁死）

| 陷阱 | 若不管会怎样 |
|---|---|
| 信封 `updatedAt` 每次同步都刷新 | 拿它当水位 → 本机永远比服务器"新" → **服务器数据再也同步不进来**（多端同步静默失效） |
| 主窗口挂载时原样回写一次 | 这次"没改动的回写"会把水位顶到"现在" → 同样是多端同步静默失效 |

**教训：给"防覆盖判据"加水位时，必须同时确认"水位不会被读取动作自己抬高"。**

### 🔴🔴 第一版修完**还是没好** —— 真事故路径在"登录那一刻"（同日第二轮）

守卫回头想读回来，读到的已是被自己人抹干净的空列表。**光记住水位没用，必须不让这次空写落盘。**
